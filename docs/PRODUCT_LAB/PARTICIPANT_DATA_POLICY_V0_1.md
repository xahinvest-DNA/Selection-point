# Participant Data Policy v0.1

**Статус:** mandatory Product Lab research boundary  
**Дата:** 15 сентября 2026 года  
**Область:** любые данные реального участника Product Lab, кроме владельца self-pilot  
**Важно:** это внутренняя исследовательская политика, а не юридическая консультация или полный privacy policy продукта.

## 1. Базовое правило

Публичный репозиторий Selection Point хранит:

- схемы;
- методологию;
- обезличенные примеры;
- агрегированные наблюдения;
- решения и ограничения исследования.

Публичный репозиторий **не хранит сырые персональные записи участников**.

## 2. До внешнего пилота

Пока `LAB_STATE.yaml` содержит:

```text
no_external_user_pilot_in_lab_0: true
```

внешний пользовательский пилот считается `unopened`.

Подключение других людей к рабочей группе, опроснику или сбору данных не должно автоматически превращать их ответы в evidence Product Lab до отдельного решения владельца о формате пилота и согласии участника.

## 3. Минимизация данных

Собирать только данные, которые нужны для конкретного исследовательского вопроса.

По умолчанию не нужны:

- полное имя;
- точная дата рождения;
- адрес;
- документы;
- данные аккаунтов;
- сведения о третьих лицах;
- подробности семейных конфликтов;
- медицинские диагнозы, если исследование не требует их и не имеет отдельного основания.

Если контекст события важен, предпочтителен класс события, например:

```text
family_stressor
work_conflict
unexpected_schedule_change
physical_discomfort
```

вместо идентифицирующего рассказа.

## 4. Идентификаторы

Для исследовательских записей используется `participant_id`, не имя.

Рекомендуемый формат:

```text
SPP-001
SPP-002
SPP-003
```

Таблица соответствия `participant_id ↔ identity`, если она вообще нужна, хранится отдельно от исследовательских данных и не публикуется в GitHub.

## 5. Согласие

До включения данных внешнего участника в исследовательский массив человек должен понимать минимум:

- что именно собирается;
- зачем;
- что Selection Point находится на исследовательской стадии;
- что участие добровольное;
- что можно прекратить участие;
- где хранятся записи;
- что может быть использовано только обезличенно/агрегированно;
- что продукт не является медицинской или психотерапевтической услугой.

Согласие на участие не означает согласия на публичную публикацию сырого материала.

## 6. Третьи лица

Участник может описывать событие, в котором фигурирует другой человек. Исследовательская запись должна по возможности сохранять функционально значимую структуру и удалять идентифицирующие подробности третьего лица.

Пример:

```text
не: имя + конкретная семейная история
а: acute family stressor → state change → realized continuation
```

## 7. Чувствительные данные

Если участник сообщает сведения о здоровье, употреблении веществ, семейных отношениях, психическом состоянии или других чувствительных областях:

- не публиковать сырой текст в открытом репозитории;
- не использовать как диагноз;
- не делать медицинских выводов;
- хранить только необходимую для исследовательского вопроса степень детализации;
- при переносе в публичную документацию обезличивать и обобщать.

## 8. Хранение

До отдельного технического решения Product Lab должен придерживаться принципа:

```text
raw participant data → private storage
public GitHub → schemas + anonymized/aggregated findings only
```

Конкретное хранилище, сроки retention и механизм удаления должны быть утверждены **до** формального внешнего пилота.

## 9. Удаление и выход

Будущий внешний пилот должен иметь понятный путь:

- прекратить участие;
- прекратить дальнейший сбор;
- запросить удаление идентифицируемых сырых записей, если это технически возможно и не противоречит обязательным правовым требованиям.

До появления такого пути внешний исследовательский пилот не должен считаться операционно готовым.

## 10. Публикация кейсов

Публичный кейс допускается только как:

- обезличенная причинная/поведенческая структура;
- агрегированный вывод;
- специально согласованная публикация.

Даже при согласии не следует публиковать детали, которые не нужны для понимания исследовательского вывода.

## 11. Граница интерпретации

Личные данные не получают более сильного evidence status только потому, что они эмоционально насыщены или подробно описаны.

```text
rich story ≠ causal proof
self-report ≠ direct observation
repeated correlation ≠ established mechanism
```

## 12. Gate внешнего пилота

До формального открытия внешнего пилота должны существовать минимум:

1. явное решение владельца;
2. research question и scope;
3. participant consent text;
4. private storage decision;
5. deletion/withdrawal procedure;
6. participant ID scheme;
7. event schema и measurement spec;
8. правило отделения raw data от public repository.

Эта политика не открывает внешний пилот. Она только создаёт необходимую границу до его обсуждения.
