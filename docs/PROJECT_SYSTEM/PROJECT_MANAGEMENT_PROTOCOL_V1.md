# Selection Point — Project Management Protocol v1

**Status:** approved operating proposal  
**Owner:** Андрей  
**Scope:** управление текущей работой, решениями, техническими задачами и данными пилота  
**Authority:** `docs/PROJECT_SYSTEM/PROJECT_SYSTEM_STATE.yaml`

## 1. Цель

Проект должен оставаться управляемым, когда методология, пилотные данные и техническая реализация находятся в разных местах. Управление строится вокруг одного текущего шага и четырёх связанных регистров.

## 2. Четыре регистра

### 2.1 Current Work

Источник: `PROJECT_SYSTEM_STATE.yaml.current_work`.

Хранит только текущий маршрут, одну цель, один главный следующий шаг, активный артефакт и границы полномочий. Если задача не относится к этому шагу, она не должна менять текущий маршрут автоматически.

### 2.2 Decision Log

Хранит утверждённые решения владельца: что решено, когда, на каком основании, что решение разрешает и чего не разрешает. Предложение не становится правилом проекта до явного решения владельца.

### 2.3 Task Register

Хранит технические и операционные задачи Codex с исполнителем, входным артефактом, критериями приёмки и проверяемым результатом. Техническая задача не может менять методологический смысл проекта.

### 2.4 Evidence/Data Register

Хранит происхождение данных: источник, участник, дата события, время отправки если известно, время импорта, состояние проверки и ограничения интерпретации. Сырые персональные данные остаются в приватном хранилище.

## 3. Допустимые статусы

`idea` → `open` → `in_progress` → `owner_review` → `approved` → `verified`

Дополнительные состояния: `blocked`, `completed_unverified`, `archived`.

`completed_unverified` означает, что выполнение заявлено, но не подтверждено проверкой. Только `verified` считается проверенным результатом.

## 4. Правила переходов

1. В любой момент существует один главный следующий шаг в `current_work`.
2. Новая идея не вытесняет текущий шаг без решения владельца.
3. Методологическое решение требует явного решения владельца.
4. Codex получает задачу после фиксации входа и критериев приёмки.
5. Импорт данных не считается завершённым без проверки дублей, конфликтов, покрытия дат и повторного запуска.
6. Изменение схемы не переписывает исходные записи; новые представления ссылаются на источник и версию преобразования.

## 5. Разделение рабочих потоков

Работа ведётся в трёх потоках:

- **курс и методология** — направление, структура, уроки, гипотезы;
- **пилот и данные** — анкеты, события, происхождение и обзоры;
- **техническая реализация** — хранилище, импорт, автоматизация и визуализация.

Пилотные данные не являются предварительным условием разработки курса. Техническая готовность не является методологическим утверждением.

## 6. Еженедельный обзор

Один раз в неделю владелец получает короткий обзор:

- выполненные и проверенные результаты;
- новые решения и открытые вопросы;
- фактическое покрытие данных;
- блокеры и конфликты;
- один следующий главный шаг;
- задачи, отправленные в архив.

## 7. Минимальный журнал изменения

Каждое существенное изменение должно отвечать на пять вопросов:

1. Что изменилось?
2. Почему это изменилось?
3. Какой источник или решение это разрешает?
4. Что теперь считается текущим?
5. Как это проверено?

Этот протокол не открывает новые Gate, не подтверждает эффективность методологии и не разрешает публикацию приватных данных.
