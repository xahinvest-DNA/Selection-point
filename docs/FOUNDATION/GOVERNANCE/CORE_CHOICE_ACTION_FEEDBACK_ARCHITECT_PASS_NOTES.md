# Core clarification — Architect pass: выбор → реализованный ход → последствия → обратная связь

**Дата:** 15 сентября 2026 года  
**Статус:** architect-pass-complete; reality-check-pending; owner-approval-pending  
**Рабочий источник:** `../SOURCE_MATERIALS/26_2026-09-15_CHOICE_ACTION_EXECUTION_FEEDBACK_BOUNDARY.md`

## 1. Архитектурный вопрос

> **Нужно ли Selection Point явно различить внутренне сделанный выбор и фактически реализованное продолжение, чтобы не приписывать неисполненному выбору последствия и обратную связь, которые реальность могла дать только на реально произошедший ход?**

Это не новый параметр ступени и не новый механизм человека. Это проверка сквозной границы core cycle.

---

## 2. Что уже утверждено

Архитектура уже содержит принципиальное различение:

```text
доступная точка выбора
→ действие
→ последствия
→ обратная связь
```

и повторяемую спираль:

```text
заметить
→ выбрать доступный ход
→ действовать
→ увидеть последствия
→ скорректировать систему
```

SP-HCM-05 утверждает, что действие создаёт новый внешний и внутренний опыт.

SP-HCM-06 уже жёстко разводит:

```text
последствия
≠ автоматически обратная связь
```

SP-HCM-07 допускает восстановление выбора после уже совершённого действия.

Protocol v4.1 содержит ещё более явную исследовательскую последовательность:

```text
допустить возможность
→ выбрать
→ действовать
→ дать реальности ответить
→ получить факт
→ скорректировать картину
```

Следовательно, owner insight **совместим с существующим ядром и выявляет недостающую явную boundary, а не требует нового HCM-положения**.

---

## 3. Где остаётся архитектурная неоднозначность

Термин `выбрать доступный ход` легко прочитать как будто выбранный ход уже стал фактическим продолжением.

Это создаёт ложную цепочку:

```text
решил сделать X
→ значит сделал выбор
→ значит сделал ход
→ значит могу оценивать feedback по X
```

Но реально возможно:

```text
решил сделать X
→ сделал Y / ничего не сделал / сделал часть X
```

Тогда реальность отвечает на **Y / фактическое бездействие / частичное исполнение**, а не на неслучившийся X.

---

## 4. Рекомендуемое минимальное уточнение core cycle

Не добавлять новый SP-HCM-10.

Вместо этого явно развести два уровня:

```text
доступная точка выбора
→ выбранное продолжение
→ фактически реализованное продолжение
→ последствия
→ обратная связь
→ обновлённая позиция
```

Ключевое отношение:

```text
выбранное продолжение
может = фактически реализованному
или ≠ ему
```

Разность между ними — самостоятельные данные о процессе исполнения.

---

## 5. Предлагаемые определения

### Выбранное продолжение

Внутренне принятое решение о том, какое доступное продолжение человек намерен реализовать из текущей позиции.

Оно реально как психический факт, но само по себе не доказывает исполнения.

### Фактически реализованное продолжение

То, что реально произошло в поведении / невмешательстве / частичном выполнении в релевантном временном окне и поэтому стало частью причинной истории следующей позиции.

Оно может быть:

- действием;
- сознательно выдержанной паузой / отказом / невмешательством;
- частичным выполнением;
- автоматическим действием, отличным от выбранного;
- неисполнением выбранного действия.

### Разрыв выбор → реализация

Наблюдаемое несовпадение между выбранным и фактически реализованным продолжением.

Это не моральный провал и не доказательство слабой воли. Его возможные причины включают:

- автоматизм;
- изменение состояния;
- забывание;
- конфликт приоритетов;
- объективное ограничение;
- изменение фактов;
- недостаток навыка;
- плохую организацию исполнения;
- сознательный пересмотр решения.

---

## 6. Что именно получает проверку реальностью

Главное различение:

> **Неисполненный выбор не получает внешней проверки как неслучившееся действие.**

Пример:

```text
выбрал отправить коммерческое предложение
→ не отправил
```

Нельзя сделать вывод:

> «рынок не отреагировал на моё предложение».

Рынок предложения не видел.

Но возникли другие реальные данные:

- решение было принято;
- исполнение не произошло;
- могли возникнуть облегчение, откладывание, забывание или сопротивление;
- фактическая траектория продолжилась без отправки.

То есть feedback относится к **реализованному продолжению и к разрыву исполнения**, а не к внешней эффективности неисполненного хода.

---

## 7. Важная поправка: внутренний выбор тоже является реальным событием

Нельзя утверждать:

```text
нет внешнего действия
→ ничего не произошло
```

Выбор может сам изменить:

- состояние;
- внимание;
- ожидания;
- напряжение;
- планирование;
- психологическую доступность следующих действий.

Поэтому более точная формула:

> **Внутренний выбор может дать feedback о внутреннем процессе и о способности исполнения, но не может заменить ответ реальности на внешнее действие, которое не произошло.**

---

## 8. Сознательное бездействие

Архитектура не должна создавать action bias.

Если человек выбрал:

- не отвечать до утра;
- не вмешиваться;
- остановить сделку;
- выдержать паузу;
- отказаться от покупки;

и действительно реализовал это невмешательство, то это **фактически реализованное продолжение**.

Следовательно:

```text
реализованный ход
≠ обязательно активное моторное действие
```

---

## 9. Частичное исполнение

Выбранный ход может быть реализован частично.

```text
выбрал запустить продукт
→ сделал лендинг
→ не открыл продажи
```

Реальность уже дала данные о создании лендинга и процессе исполнения, но ещё не дала market feedback на запуск, которого не было.

Практическое правило:

> **Не расширять область обратной связи дальше реально выполненной части.**

---

## 10. Связь с SP-S4-P13

P13:

> **Выбор совершается в моменте. Траектория обнаруживается во времени.**

Core clarification добавляет:

> **Траектория во времени описывается фактически реализованными продолжениями и их последствиями, а не только серией внутренних решений.**

Это усиливает P13, не меняя его смысл.

Пример:

```text
14 дней:
каждый день выбираю работать над проектом
+
реально работаю 2 дня

→ серия намерений показывает направление
→ серия реализованных ходов показывает фактическую траекторию
→ разрыв между ними является отдельными данными
```

## 11. Архитектурные следствия при будущем утверждении

Рекомендуется не новый HCM claim, а ограниченное cross-cutting уточнение:

1. `ARCHITECTURAL_DECLARATION.md` — явно вставить границу `выбор ≠ исполнение`;
2. `HUMAN_CHANGE_MODEL.md` / canonical HCM — уточнить core cycle через `выбранное → реализованное продолжение`;
3. `TERMS_REGISTRY.md` — при необходимости ввести термины для выбранного и реализованного продолжения либо один термин `фактически реализованное продолжение`;
4. `RISKS_AND_BOUNDARIES.md` — добавить риск засчитывания внутреннего решения как действия;
5. P13 — только cross-reference, без изменения утверждённого claim;
6. Phase 5 — практики должны фиксировать не только «что решил», но и «что фактически произошло».

Protocol v4.1 менять по смыслу, вероятно, не требуется: он уже содержит корректную последовательность `выбрать → действовать → получить факт`.

## 12. Architect verdict

**Самостоятельная сквозная дельта есть**, но она является boundary/clarification, а не новым психологическим механизмом.

Сильнейший кандидат:

> **Selection Point открывает возможность другого продолжения, но внутренний выбор не засчитывается как реализованный ход. Фактическую траекторию изменяет то продолжение, которое реально произошло; последствия этого продолжения дают данные, а обратной связью они становятся, когда способны скорректировать следующий цикл.**

Коротко:

> **Выбрать ≠ сделать. Сделать ≠ получить желаемое. Получить последствия ≠ использовать обратную связь.**

Перед утверждением требуется Reality Check и Red Team.
