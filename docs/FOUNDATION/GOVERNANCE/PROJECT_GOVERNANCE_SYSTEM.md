# Система управления проектом Selection Point

**ID:** SP-GOV-01  
**Статус:** действующий обязательный регламент  
**Дата:** 28 августа 2026 года  
**Основание:** явное решение Андрея внедрить корректировки архитектуры управления без изменения утверждённого смысла метода.

---

## 1. Назначение

Этот документ отделяет четыре функции, которые ранее частично дублировались:

```text
текущий статус проекта
≠ правила работы
≠ утверждённый смысл метода
≠ историческая фиксация решения
```

Для них действуют разные источники:

- текущий статус — `../PROJECT_STATE.yaml`;
- правила процесса — `../PROJECT_OPERATING_PROTOCOL.md`;
- смысл — полный теоретический и канонический слои;
- история решений — датированные checkpoints и git history.

Ни один производный статусный документ не может становиться самостоятельной параллельной базой состояния.

---

## 2. Единственный источник текущего состояния

`docs/FOUNDATION/PROJECT_STATE.yaml` является единственным авторитетным репозиторным источником текущей фазы, ступени, последнего утверждённого параметра, следующего кандидата и явной паузы.

При расхождении производного документа с manifest:

1. работа не продолжает архитектуру по устаревшему документу;
2. проверяется последнее явное решение Андрея;
3. manifest исправляется, если он не соответствует этому решению;
4. затем синхронизируются производные документы.

`README.md`, `CURRENT_PROJECT_STATE.md`, `docs/CURRENT_STATE.md`, индексы и Codex README являются представлениями состояния, а не самостоятельными источниками текущей остановки.

---

## 3. Два интеллектуальных режима перед утверждением

### 3.1. Architect mode

Задача — построить наиболее сильное, связное и точное объяснение рассматриваемого архитектурного вопроса.

Architect обязан:

- опираться на утверждённые положения;
- показывать механизм и различения;
- не открывать соседние параметры;
- явно отделять авторскую гипотезу от внешне подтверждённого знания.

### 3.2. Red Team / Falsification mode

До утверждения нового архитектурного положения ChatGPT обязан отдельно попытаться разрушить собственное предложение.

Минимальный набор вопросов:

1. Какое сильное альтернативное объяснение существует?
2. Какой наблюдаемый случай сделал бы тезис неверным или потребовал бы его существенного пересмотра?
3. Не описываются ли одним термином несколько разных механизмов?
4. Можно ли различить новый параметр по фактам, а не только внутри языка Selection Point?
5. Какой контрпример или граничный случай наиболее опасен для формулировки?
6. Не превращается ли объяснение в нефальсифицируемую схему, где любой исход подтверждает модель?

Red Team не имеет права автоматически отменять архитектурную гипотезу. Его функция — сделать стоимость утверждения выше стоимости красивой формулировки.

---

## 4. Continuous Reality Check

Фаза 3 больше не является периодом только внутреннего построения системы.

Параллельно архитектуре постоянно действует контур проверки:

```text
архитектурная гипотеза
↕
внешние исследования
реальные эпизоды
контрпримеры
альтернативные объяснения
наблюдаемость различения
условия опровержения
```

Continuous Reality Check не является ранним пилотом курса и не открывает Фазы 4–8.

Он отвечает на более узкие вопросы:

- существует ли описываемое различение;
- можно ли его наблюдать;
- не противоречит ли оно доступным данным;
- где проходит граница применимости;
- что могло бы его опровергнуть;
- какие формулировки требуют внешней проверки до публичного использования.

Подробный регламент находится в `REALITY_CHECK_PROTOCOL.md`.

## 5. Delta-first и периодическая консолидация

После каждого нового параметра создаётся локальная delta-карта, содержащая только новое:

- claim;
- новые термины, если они действительно появились;
- новые общие риски, если они действительно появились;
- evidence questions;
- cross-references;
- решение по визуальным моделям.

Большие общие реестры не переписываются после каждого параметра.

Плановая консолидация выполняется:

- после P05;
- после P10;
- после P13;
- на границе ступени;
- либо по отдельному решению Андрея, если накопленные дельты создают навигационный риск.

При консолидации:

```text
active deltas
→ проверка на дубли
→ перенос в общие реестры
→ проверка ссылок
→ delta остаётся историческим источником своего изменения
```

Это правило заменяет прежнее требование переписывать `CLAIMS_REGISTRY.md`, `EVIDENCE_MAP.md` и `CROSS_REFERENCE_MAP.md` после каждого параметра.

---

## 6. Матрица 5 × 13 — исследовательский каркас, а не закон

Пять ступеней и тринадцать параметров остаются действующей рабочей архитектурой.

Но система обязана допускать три результата исследования следующей ячейки:

1. **новая дельта существует** — создаётся новый параметр;
2. **новой дельты нет** — параметр может быть зафиксирован как `zero-delta`, если различение полностью покрыто предыдущей архитектурой;
3. **каркас недостаточен** — по явному решению Андрея может быть добавлен, разделён, объединён или пересмотрен параметр.

Запрещено создавать различие только потому, что таблица требует заполнить ячейку.

Критерий параметра:

> Он должен описывать наблюдаемое или функционально необходимое различие, а не поддерживать симметрию схемы.

---

## 7. Управление текущим статусом

После изменения архитектурного статуса сначала изменяется:

`PROJECT_STATE.yaml`.

Затем синхронизируются только необходимые производные поверхности:

1. `CURRENT_PROJECT_STATE.md`;
2. `docs/CURRENT_STATE.md`;
3. `README.md`;
4. индекс активного теоретического слоя;
5. индекс канонического слоя;
6. индекс библиотек;
7. индекс визуальных моделей, только если его содержание реально изменилось;
8. Codex README, только если изменился исполнимый контекст;
9. новая контрольная точка.

Operating protocol не дублирует текущий прогресс по параметрам.

---

## 8. Правило против рассинхронизации

Перед закрытием рабочего цикла выполняется consistency check:

```text
PROJECT_STATE.yaml
= CURRENT_PROJECT_STATE
= docs/CURRENT_STATE
= README
= active theory index
= canonical index
= library index
= active checkpoint
```

Проверяется не буквальное совпадение текста, а одинаковая семантика статуса.

Любой файл с противоречащим активным статусом считается дефектом документации.

Исторические checkpoints и addenda исключаются из этой проверки, если явно имеют историческую дату и не объявлены активными.

---

## 9. Терминологический предохранитель перед внешней доставкой

Формулировка «создание собственной реальности» остаётся частью утверждённого внутреннего HCM-09 и не меняется этим governance-решением.

До Фазы 4 она обязана пройти отдельный terminology/public-language review из-за риска эзотерической, солипсистской или магической трактовки.

Кандидаты для внешнего языка должны проверяться без автоматической замены канона, например:

- «участие в создании следующей позиции»;
- «формирование собственной траектории из фактической позиции».

Изменение HCM-09 возможно только отдельным содержательным обсуждением и явным утверждением Андрея.

---

## 10. Главное правило

> Selection Point применяет к собственной разработке тот же принцип, который предъявляет к модели человека: модель остаётся рабочей только пока реальность сохраняет возможность её изменить.

Поэтому архитектурная согласованность является необходимым, но недостаточным условием продолжения проекта.
